# خطة تبسيط BabiesPicks على نمط موقع طارق

> للمُنفّذ: استخدم superpowers:executing-plans عند اعتماد التصميم وبدء التنفيذ، مع اختبارات انحدار للسلوك المتغير. لا تفويض لوكلاء دون حصر الملكية واتباع تعليمات المستخدم. هذه وثيقة مقترحة للمراجعة، وليست تصريحًا بالنشر أو حذف البيانات أو تنفيذ تغييرات الإنتاج.

**الهدف:** تحويل BabiesPicks إلى موقع منتجات ومحتوى يديره المالك أو مساعده عبر MCP، مع إبقاء روابط العمولة والبيانات والروابط العامة، والاستغناء عن منظومة الوكلاء والتشغيل المتداخلة داخل التطبيق.

**البنية المقترحة:** Next.js لعرض الموقع ومسارات القراءة والتحويل؛ PostgreSQL لحفظ البيانات؛ خدمة MCP مستقلة لإدارة المحتوى. تتشارك الواجهة وخدمة MCP في منطق أعمال صغير وفي حزمة قاعدة البيانات، دون اتصالات HTTP داخلية ضرورية لقراءة كل صفحة. البحث والتحليل والكتابة مهام للمساعد الخارجي؛ التطبيق يتحقق من البيانات والصلاحيات ويحفظها وينشرها.

**التقنيات:** الاحتفاظ بـ Next.js وTypeScript وPrisma وPostgreSQL وnext-intl وpnpm الموجودة. لا ترقية إصدارات أو نقل استضافة ضمن مشروع التبسيط. إضافة MCP باتباع نمط موقع طارق بعد مراجعة النسخة الفعلية من تنفيذه، مع فصل أسرار وبيانات واتصالات الموقعين.

**المواصفة:** الأقسام 1–7 من هذه الوثيقة. مهام التنفيذ في القسم 8، والقبول والانتقال في القسمين 9–10. جميع المسارات البرمجية النسبية أدناه تقع داخل `/Users/tariq/code/babiespicks` ما لم يُذكر غير ذلك.

**الحالة بتاريخ 21 أكتوبر 2026:** مبنية على قراءة النسختين المحليتين؛ لم يُفحص الإنتاج أو حجم بياناته أو إعداداته أو نجاح النشر الحالي. لا تغييرات على كود المشروعين، ولا تثبيت أو تشغيل أو نشر. القياس الكامل للتوكنات غير متاح؛ لقطة الاستخدام متأخرة وتشمل سياق المحادثة، ولا تصلح لنسبة استهلاك الخطة وحدها.

## 1. ما الذي نغيّره ولماذا؟

موقع طارق يفصل إدارة المحتوى عبر MCP عن عرضه. نموذج المقال فيه حالات DRAFT / REVIEW / PUBLISHED / ARCHIVED، وإصدارات وسجل تعديلات، وصلاحية نشر مستقلة. BabiesPicks يجمع واجهة عامة وNestJS ووكلاء لاكتشاف المنتجات وتحليلها وكتابتها وDify وAI OS ومسارات موافقة متعددة.

ملاحظة مثبتة من الكود: `apps/api/src/features/cron/cron.service.ts` يعيد تشغيل `runProductPipeline` أثناء تحديث الأسعار كل ست ساعات؛ وهذه الدالة تجمع البيانات وتحاول تحليل المراجعات وإصدار التقييم ونشره. في المقابل، جزء من توليد مسودات العروض في `offer-enrichment.service.ts` يستخدم محتوى أوليًا، وبعض حقول التحويلات في التحليلات تعاد بقيمة صفر. كثرة الشاشات لا تعني اكتمال كل وظائفها.

التبسيط المقصود ليس تغيير ألوان BabiesPicks لتشبه موقع طارق، ولا دمج الموقعين في تطبيق أو قاعدة واحدة. نأخذ طريقة الإدارة والفصل بين المحتوى والمساعد، ونحافظ على هوية منتجات الأطفال.

## 2. القرارات المقترحة والافتراضات

- العربية أساسية؛ نحافظ على الإنجليزية الموجودة ومسارات `/ar` و`/en`. نشر لغة لا يشترط اختراع ترجمة للغة أخرى؛ البديل اللغوي يظهر بوضوح، ولا ينتج محتوى فارغًا أو وسم لغة مضللًا.
- المنتجات والمحتوى لهما مصدر بيانات واحد؛ لا نبني سلسلة جديدة من TrendSignal ثم ProductDraft ثم OfferEnrichment ثم PublicOfferDraft لكل منتج جديد.
- نحتفظ بالتصنيفات والمتاجر والكوبونات والمقارنات وأدوات الاختيار والحساب الموجودة، بعد حصر اعتمادها الفعلي. نصلح تكاملها مع المصدر الجديد بدل توسيع وظائفها.
- التقييم الحالي اختياري ومخزّن، مع مصدر وتاريخ وبيان أنه تقييم تحريري. لا تشغيل تلقائي لنموذج عند قراءة الصفحة أو تغيير سعر؛ لا ادعاء سلامة أو شهادة دون دليل.
- إدارة الموقع عبر MCP هي المسار الأساسي. تبقى صفحات الإدارة القديمة خلال الانتقال فقط؛ الوجهة النهائية لا تتطلب لوحة AI OS بديلة أو محررًا جديدًا.
- يُقترح دعم روتين خارجي يومي، مع تشغيل عند الطلب أيضًا. العدد والتوقيت ومصدر التشغيل ليست قرارات معتمدة بعد. لا تُنشأ أتمتة أو جدولة الآن.
- افتراضيًا ينشئ الروتين مسودات؛ نشر تلقائي يحتاج تفويضًا محددًا من المالك يحدد الأنواع والحدود. طلب هذه الخطة لا يمنح هذا التفويض.
- X وتيليجرام ليسا شرطًا لتشغيل الموقع. نحفظ السجلات والمهام القائمة ونحدد مصيرها قبل إيقاف التنفيذ القديم؛ أي نشر لاحق يستخدم موصلًا خارجيًا متاحًا ومصرحًا أو مؤجلًا، دون بناء منصة اجتماعية داخلية جديدة.
- الحسابات والأسرار مستقلة بين الموقعين؛ لا نسخ لملفات `.env` أو كلمات المرور أو المنح أو محتوى طارق.

## 3. تجربة الاستخدام بعد التبسيط

أمثلة طلبات من المحادثة:

- «أضف عربة الأطفال هذه، وسجل سعرها وروابط شرائها ومصدر المعلومات، واحفظها للمراجعة».
- «اكتب مقارنة بين هذه المنتجات باستخدام البيانات الموثقة، واعرض المسودة».
- «حدّث سعر هذا المنتج فقط، ولا تعدّل وصفه أو تقييمه».
- «انشر المقال الذي راجعته بالإصدار الحالي»، أو «ألغ نشر العرض المنتهي».
- «اعرض أكثر المنتجات حصولًا على نقرات هذا الأسبوع».

الموقع يعرض للزائر الاسم والصورة والمعلومات والمميزات والعيوب والتقييم إن وجد، والسعر وتاريخ التحقق والمتاجر. الشراء يبقى في المتجر الخارجي. لا رسوم افتراضية لمبيعات أو أرباح غير متصلة بمصدر فعلي.

## 4. البنية والملكية

```text
المساعد / روتين خارجي مصرح
           │ OAuth + MCP
           ▼
      apps/mcp ──────────┐
                        ▼
                 packages/domain ── packages/db ── PostgreSQL
                        ▲
                        │
                apps/web (Next.js)
              عرض + بحث + /go + إعادة تحقق الكاش
```

الخدمات الدائمة النهائية: قاعدة بيانات، ويب، MCP. التخزين الدائم للوسائط يبقى منفصلًا عن عمر الحاوية. لا حاجة إلى NestJS أو Dify أو Redis لتشغيل هذا المسار بعد اكتمال الانتقال، بشرط إثبات انتهاء اعتماد الوظائف المحفوظة عليها. خدمة ترحيل قاعدة البيانات عملية تشغيلية عند الإصدار، وليست وكيلًا دائمًا.

حزم التنفيذ المقترحة:

| الحزمة | الملكية | تعتمد على |
|---|---|---|
| البيانات | `packages/db` وترحيلات Prisma وأدوات النقل | جرد البيانات وخريطة الحالات |
| منطق الأعمال | `packages/domain` | قاعدة البيانات والصلاحيات المتفق عليها |
| أدوات الإدارة | `apps/mcp` | عقود منطق الأعمال |
| العرض والتحويل | `apps/web` | عقود القراءة والأسعار والحالات |
| الأتمتة والإغلاق | تعليمات التشغيل ومهام خارجية معتمدة | MCP والتحويل وتجربة النقل |

التنفيذ المقترح يبدأ متسلسلًا بحزمة البيانات والعقود. يمكن لاحقًا فصل MCP والويب إذا استقرت العقود وملكية الملفات. التخطيط الحالي inline؛ لا حاجة إلى وكلاء لإنتاج هذه الوثيقة، ولا تفويض قائم للتنفيذ في هذه المرحلة.

## 5. البيانات والحالات

### 5.1 ما نحتفظ به

إعادة استخدام الجداول والهوّيات الحالية قدر الإمكان: Product، ProductTranslation، ProductSpec، ProductPrice، ProductReviewSummary، Verdict، Store، Category، ContentPage، ContentPageTranslation، Coupon، AffiliateClick، ومشتركي النشرة وسجلات الوسائط والنشر إن وُجدت فعليًا.

لا نحذف جدولًا قديمًا في الترحيل الأول. يُنقل مخطط Prisma إلى `packages/db/prisma/schema.prisma` مع الحفاظ على أسماء الجداول `@@map` والقيود وترتيب الترحيلات. يُراجع تاريخ الترحيلات الحقيقي قبل التغيير؛ لا تنفيذ `db push` على الإنتاج ولا افتراض أن وصف AGENTS القديم يعكس كل الترحيلات الحالية.

### 5.2 الحالات الجديدة

للمنتج والمحتوى حقل موحّد `publishStatus: DRAFT | REVIEW | PUBLISHED | ARCHIVED` مع `version` و`publishedAt`. يُضاف أولًا بجانب الحالات القديمة. كود التوافق هو الكاتب الوحيد أثناء الانتقال، ثم تصبح الحالة الجديدة المرجع الوحيد بعد التحويل.

خريطة مبدئية يجب اختبارها على بيانات فعلية معزولة:

- المحتوى المنشور فعليًا (`isPublished=true`) يصبح PUBLISHED، مع الحفاظ على تاريخ النشر أو توثيق فقده دون اختراع تاريخ قديم.
- تعارض الحالة مع علامة النشر يُدرج في تقرير منفصل ويُحسم بما يطابق الظهور العام المثبت، دون نشر محتوى جديد آليًا.
- المحتوى SCHEDULED غير المنشور يصبح REVIEW؛ موعده وتفويضه يُنقلان كطلب تنفيذ منفصل، ولا يختفي الموعد ولا ينفذ تلقائيًا أثناء الاستيراد.
- المنتجات العامة حاليًا تُحدد بمنطق القراءة الموجود وصفحاتها؛ لا نستنتج أن isActive أو اسم ACTIVE وحده يثبت النشر.
- المسودات المرفوضة تبقى DRAFT مع ملاحظة الرفض، أو ARCHIVED إن كانت مغلقة أصلًا؛ لا تُنشر.
- ProductDraft وArticleDraft وContentDraft والعروض تُربط بالمنتج أو المحتوى النهائي عبر جدول خريطة نقل. العناصر غير القابلة للمطابقة تُحفظ كمسودات أو سجلات إرث؛ لا دمج بالنص المتشابه وحده.
- PublicOffer المنشور يحتفظ بمساره `/offers/[slug]` وبمحتواه وعلاقاته، ويمكن تمثيله كنمط محتوى OFFER في النموذج الموحّد، مع رابط المصدر القديم.

### 5.3 الإصدارات والمصادر

كل تعديل يتحقق ذريًا من `expectedVersion` ثم يزيد الإصدار ويسجل Revision في المعاملة نفسها. التعارض يرجع VERSION_CONFLICT؛ لا استبدال صامت ولا تكرار تلقائي للكتابة بإصدار مختلف.

الإنشاء والتعديل يدعمان idempotencyKey مع نطاق الاتصال ونوع العملية، وسجل نتيجة مختصر يمنع التكرار عند إعادة الطلب. نفس المفتاح مع مدخلات مختلفة يعيد IDEMPOTENCY_CONFLICT.

تُحفظ مصادر الحقائق والتقييمات: URL المصدر، تاريخ الاطلاع، الحقل المدعوم، وصف مختصر للدليل. لا تُملأ مراجعات مشترين أو أرقام مبيعات أو شهادات من تخمين المساعد. المعلومات المجهولة تبقى مجهولة.

تحرير محتوى منشور تغيير عام فوري عند نجاح إبطال الكاش؛ لذلك يحتاج تفويض النشر وعلمًا صريحًا `allowPublishedEdit:true`. لا نفترض أن تعديل منشور يُحفظ سرًا كمسودة. هذا يحافظ على بساطة سجل واحد دون منظومة مسودات مزدوجة.

## 6. العقود التي يتشاركها MCP والويب

العقود أدناه أسماء مستهدفة جديدة؛ تُثبّت كأنواع مصدّرة من `packages/domain/src/contracts.ts` قبل تقسيم التنفيذ.

- `ActorContext`: هوية الاتصال وصلاحياته، وتأتي من الخادم بعد التحقق لا من مدخلات المستخدم.
- `PublicationStatus`: الحالات الأربع أعلاه.
- `ProductInput`: الاسم، slug اختياري، العلامة، التصنيف، الترجمات، الصورة، المواصفات، المصادر، ملخص المميزات والعيوب، والتقييم التحريري الاختياري.
- `ContentInput`: النوع `BEST_LIST | PRODUCT_REVIEW | BUYING_GUIDE | OFFER`، العنوان والمتن واللغة وslug والعلاقات بالمنتجات والتصنيف والصورة وحقول SEO والمصادر.
- `WriteOptions`: `{ actor, idempotencyKey, expectedVersion?, allowPublishedEdit? }`. expectedVersion إلزامي لكل تحديث أو حالة، وغير مطلوب للإنشاء.
- `ProductView` و`ContentView`: شكل موحّد صريح للقراءة العامة، لا يعرض ملاحظات الإدارة أو سجلات الموافقة. تُوفّر محولات توافق لشكل الواجهة الحالية أثناء الانتقال.
- `createProduct(input, options)` و`updateProduct(id, patch, options)` و`createContent(input, options)` و`updateContent(id, patch, options)` ترجع `{ id, slug, version, publishStatus }`.
- `setPublicationStatus(entityType, id, targetStatus, options)` يحتاج إصدارًا متوقعًا وتأكيدًا صريحًا وتفويضًا عند النشر/الأرشفة/إلغاء النشر؛ يحدد تاريخ النشر دون تغييره في كل تعديل.
- `recordPriceObservation({ productId, storeId, amount, currency, inStock, sourceUrl, checkedAt }, options)` يضيف ملاحظة سعر فقط؛ لا يستدعي تحليلًا أو كتابة أو تغيير حالة نشر.
- `resolvePurchaseTarget({ productId, storeId? }, now)` يرجع وجهة من سجل عروض مؤهل، أو نتيجة NO_OFFER؛ لا يقبل عنوان إعادة توجيه من query string.
- `getClickStats({ from, to, productId? })` يعيد نقرات فقط، دون حقل أرباح أو تحويلات مزعوم.

### الأسعار وروابط العمولة

نحتفظ بتاريخ ProductPrice، ونختار أحدث ملاحظة لكل متجر أولًا ثم نقارن الأسعار؛ لا نختار أدنى سعر في كامل التاريخ. المتجر يجب أن يكون نشطًا والعرض متاحًا وغير منتهي الحداثة. المقترح أن الحد الافتراضي 48 ساعة ويمكن تغييره بإعداد واحد؛ هذا قرار تصميم مقترح لا وصف لسلوك قائم.

نحتفظ بالتواريخ القديمة بلا تزوير. العروض القديمة تظهر «تحقق من السعر لدى المتجر» ولا توصف بأنها الأقل حاليًا. إن لم يوجد عرض حديث لا نوجه تلقائيًا إلى سعر قديم باعتباره أفضل سعر. يمكن عرض رابط متجر معلوم بعنوان واضح دون وعد بالسعر.

نبني رابط العمولة عند التحويل انطلاقًا من رابط منتج أصلي موثوق وإعداد شبكة المتجر. الروابط المغلفة القديمة تُحفظ؛ لا نفك روابط لا نعرفها ولا نضيف غلافًا ثانيًا. HTTPS وقائمة وجهات مسموح بها للشبكة والمتجر، دون جلب URL تعسفي من الخادم.

طلبات `/go/:productId/:storeId` و`/go/best/:productId` القديمة تُحفظ كعقود. يجب خدمة hostname القديم أيضًا؛ نقل صفحات الويب وحده لا يصلح الروابط الخارجية إلى API السابق. غياب العرض يعرض حالة مفهومة أو وجهة متجر معروفة وفق العقد، ولا يحوّل لمنتج أو متجر آخر دون وضوح. تعطل تسجيل النقرة لا يعطل تحويلًا صالحًا.

## 7. أدوات MCP والأتمتة

أسماء الأدوات المقترحة:

- `bp_get_capabilities`: قدرات الاتصال وحدوده، بلا أسرار.
- `bp_list_products`, `bp_get_product`, `bp_create_product`, `bp_update_product`.
- `bp_list_content`, `bp_get_content`, `bp_create_content`, `bp_update_content`.
- `bp_set_status`: حالة المنتج أو المحتوى وفق عقد الصلاحيات والإصدارات.
- `bp_list_stores`, `bp_upsert_store`, `bp_list_categories`, `bp_upsert_category`؛ تحديث العلاقات لا ينشئ متجرًا مكررًا بالاسم.
- `bp_list_coupons`, `bp_upsert_coupon`؛ انتهاء الصلاحية يُحسب عند العرض حتى دون كرون.
- `bp_record_price`, `bp_upload_image`, `bp_get_click_stats`.

تأخذ أدوات التعديل expectedVersion، وتعيد الأخطاء المعروفة NOT_FOUND / INVALID_INPUT / VERSION_CONFLICT / PUBLISH_FORBIDDEN / CONFIRMATION_REQUIRED / IDEMPOTENCY_CONFLICT. الصور تُرفع إلى تخزين دائم بصيغ PNG/JPEG/WebP، بحد مقترح 1MB للصورة، ومسارات `/media` مستقرة. لا تُنسخ جلسات OAuth أو منح موقع طارق؛ نستفيد من نمطه مع تحقق توكن الجمهور/المصدر وسياسة النشر مستقلة.

نعيد التحقق من كاش الصفحات والقوائم والتصنيفات المتأثرة. إذا حُفظ التعديل وفشل إبطال الكاش، يعيد الخادم نجاح الحفظ مع تحذير إعادة التحقق ومرجع العملية، ويتيح إعادة إبطال الكاش دون إعادة الكتابة. لا يعيد خطأ مضللًا يدفع المساعد لتكرار الإنشاء.

الأتمتة المقترحة روتين واحد يومي خارج التطبيق: يقرأ القدرات والإعدادات، يختار دفعة محدودة، يجمع مصادر متاحة، يحدث الأسعار المؤكدة، يجهز مسودات، ويعرض ما يحتاج مراجعة. عند النشر المصرح يقرأ النسخة الأخيرة ويستخدم مفتاحًا ثابتًا للعملية. الجلب المحجوب يبقى فشلًا موثقًا ولا ينتج سعرًا أو مراجعات مختلقة.

لا نعتمد على جلسة محادثة مفتوحة لتحقيق الجدولة. يُختار مشغّل خارجي متاح فعليًا ويُختبر لاحقًا؛ إذا لم يتوفر يبقى التشغيل عند الطلب ويُذكر أن اليومي غير مفعّل. تعطل المساعد لا يعطل الموقع. إشعارات الروتين تكون عند تغيير مهم أو فشل يحتاج تدخلًا، لا رسالة مكررة لكل تشغيل.

النشر المؤجل طلب خارجي محدد للعنصر والإصدار والوقت بـ Asia/Riyadh والتفويض؛ مهمة الموعد التي تجد إصدارًا مختلفًا تتوقف للمراجعة. إعادة تشغيل الروتين لا تنشئ مقالات مكررة ولا تنشر مرتين.

## 9. التحقق ومعايير الاكتمال

أوامر مستهدفة تضاف وتُختبر أثناء التنفيذ، وليست أوامر موجودة حاليًا: `pnpm test:simplification` لاختبارات المجال وMCP، `pnpm test:migration` لـ PostgreSQL المعزول، `pnpm test:acceptance` لاختبارات المتصفح وعقود المسارات، `pnpm verify:migration -- --report <path>` للمطابقة. يُمنع تشغيلها على إنتاج بالخطأ؛ تتطلب اختبارات النقل اسم قاعدة اختبار محددًا وتتحقق منه قبل أي كتابة.

الأوامر الموجودة الآن في المشروع: `pnpm build`, `pnpm type-check`, `pnpm lint`, `pnpm test`. تُفحص إمكانية تشغيلها أولًا؛ فشل قائم يُفصل عن فشل التغيير ولا يُخفى. أثناء التنفيذ اختبارات مركزة لكل حزمة؛ في الدمج النهائي فحص الأنواع والبناء والاختبارات المناسبة مرة بعد استقرار التغييرات، وتُكرر فقط بعد تغيير أو مشكلة تستدعي ذلك.

خمس حالات يجب ألا تفلت من المراجعة:

1. تضارب حقول الحالة القديمة قد ينشر مسودة أو يخفي صفحة قائمة: تغطيه المهمة 2 ومطابقة routes.
2. قديم الأسعار قد يظهر «الأرخص» اليوم: تغطيه المهمة 3 بزمن ثابت وأسعار متعددة لكل متجر.
3. أدوات تحرير المحتوى قد تتجاوز النشر أو تتعارض: تغطيها المهمتان 3 و4 بمصادقة حقيقية واختبار معاملتين متزامنتين على PostgreSQL معزول.
4. فشل الشبكة بعد نجاح الكتابة قد يكرر المنتج/المقال أو يخفي فشل الكاش: تغطيه المهمتان 4 و6 بفصل الحفظ عن إعادة التحقق وidempotency.
5. الرجوع بعد تشغيل النسخة الجديدة قد يفقد كتابات أو يعيد نشرًا اجتماعيًا: تغطيه المهمتان 7 و8 بتجربة فارق بيانات وكاتب واحد.

يُعتبر التبسيط مكتملًا حين:

- جميع المسارات العامة المحصورة لها نفس المحتوى أو تحويل دائم صحيح؛ لا تسرب لمسودة أو ملاحظات داخلية.
- الأعداد والعلاقات والهوّيات والتواريخ والنقرات والوسائط مطابقة لتقرير النقل؛ كل فرق موضح ومقبول.
- دورة إنشاء/مراجعة/نشر/إلغاء نشر تعمل عبر MCP، مع تفويض وإصدارات وسجل، وتظهر النتيجة العامة بعد إعادة تحقق الكاش.
- التحويل إلى المتجر وروابط العمولة واختيار السعر الحديث تعمل حتى عند فشل قياس النقرة.
- تحديث السعر لا يستدعي نموذجًا ولا يغير رأيًا تحريريًا، وعرض الموقع لا يحتاج حساب ذكاء اصطناعي.
- التشغيل اليومي مثبت إن كان معتمدًا ومفعّلًا؛ وإلا يُسجّل بوضوح أن التشغيل عند الطلب فقط.
- الخدمات النهائية المطلوبة فقط تعمل، والرجوع مجرب، ولا اختبارات تستخدم خدمات الإنتاج أو تعدلها.
- لا ادعاء بتحسن زمن أو استهلاك أو مصاريف إلا بقياس قبل/بعد تحت حمل ومحتوى متقاربين. انخفاض عدد الخدمات وحده لا يثبت مقدار التوفير.

## 10. الانتقال والتسليم وحدود القرار

ترتيب التشغيل: جرد ونسخة قابلة للاستعادة ← إضافات متوافقة ← مصدر ومنطق موحد ← MCP ← الواجهة والتحويل ← تجربة مجدولة ومعزولة ← تجميد كتابة وناشرين قدامى ← نقل أخير ومطابقة ← تحويل معتمد ← مراقبة ← تقاعد القديم.
